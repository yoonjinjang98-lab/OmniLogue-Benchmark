# plugins/methods/ — 베이스라인 (B의 lane)

이 아래 하위 디렉터리 하나하나가 baseline 하나입니다: `meta.json` + `method.py`로
`src/dialogue_benchmarks/contracts.py`의 `Method` 계약을 구현합니다. 전부
독립적(self-contained)이라 — baseline을 추가하거나 고치는 데 `src/`를 건드릴
필요가 없습니다. LLM이나 임베딩 호출은 전부 `dialogue_benchmarks.llm.complete()`/
`embed()`를 거치며, `anthropic`/`openai`를 직접 부르지 않습니다 (저장소 루트
`CLAUDE.md` 참고).

다섯 baseline family와 그 이유는 저장소 루트의 `BASELINE_METRIC_PLAN.md` §4에
정의돼 있습니다 — 뭘 다음에 할지/왜 할지의 근거는 그 문서가 원본(source of
truth)이고, 이 README는 지금 이 디렉터리에 실제로 뭐가 있는지 보여주는
스냅샷일 뿐입니다.

`modeling_encoder_decoder.py`의 forward()가 `.cuda()`를 하드코딩해서 CPU 환경에서 아예 실행 불가 — `.to(device)`로 수정. ③ `generation_utils.py`의 `generate()`가 `token_type_ids`를 `greedy_search()`엔 넘기면서 `sample()`/`beam_search()`/`beam_sample()`엔 안 넘겨서, **빔서치(=upstream의 `predict()`가 실제로 쓰는 디코딩 방식)를 쓰면 무조건 TypeError** — 세 곳 다 인자 추가해서 수정. ④ `EncoderDecoderModel.forward()`가 실제론 3-튜플을 반환하는데 `sample()`/`beam_search()`/`beam_sample()`은 2개로만 unpack해서 ③을 고치고 나면 바로 ValueError — `greedy_search()`는 이미 3개로 올바르게 unpack하고 있어서 그 패턴대로 수정. 두 버그(③+④) 조합은 **upstream 자신도 빔서치 디코딩 경로를 마지막 수정 이후로 한 번도 실행 안 해봤다는 뜻**(무조건 실패하는 버그라 예외 케이스가 아님). **초기 검증**(실제 학습 전): tiny random-weight BERT 체크포인트로 인코더+디코더1+디코더2+빔서치 전체 파이프라인을 실제로 돌려서(`Method` 전체, conversation 2개 연속) 에러 없이 동작 확인. **실제 학습 완료(2026-09-11)**: upstream 자체 학습 드라이버(`bertoverbert.py`/`dataloader.py`/`evaluations.py`/`preprocess.py`, `training/` 아래 벤더링, 이미 벤더링된 `xlibs`를 그대로 재사용)를 가져와서 실제 ConvAI2(`prepare_convai2_txt.py`로 이 저장소 parquet을 upstream 원본 텍스트 포맷으로 변환, train 118,294/val 13,144/test 7,801)와 실제 MNLI(`prepare_mnli.py`로 `nyu-mll/glue`의 mnli에서 entailment/contradiction 추출, 130,899/130,903쌍 — README가 학습용으로 명시한 건 DNLI가 아니라 MNLI임, DNLI는 평가 전용)로 upstream 기본값 그대로(20 epoch, batch 64) 학습 — 서브샘플 없음. 학습 자체에선 새로 발견된 버그 없음(`modeling_encoder_decoder.py`의 `ul_training` 플래그가 negative/positive unlikelihood 두 forward pass에서 비대칭으로 쓰이는 게 처음엔 버그처럼 보였지만, `modeling_bert.py`의 실제 loss 계산을 보면 의도된 설계 — negative는 로짓 부호를 뒤집어 unlikelihood loss를, positive는 평범한 NLL을 쓰는 것). 최종 체크포인트(epoch 19)를 `$DIALOGUE_BENCHMARKS_DATA/checkpoints/bob/final`에 저장(중간 epoch 3~18 체크포인트는 삭제 — `bertoverbert.py`가 토크나이저 파일은 저장 안 해서 `bert-base-uncased` 토크나이저를 체크포인트 디렉터리에 같이 복사해둠). **검증**: 이 실제 체크포인트로 `Method` 전체를 실행해서 persona 관련 단어가 실제로 나오는 것 확인(예: hunting persona → "hunting, hunting, and hunting", pizza persona → "pizza it is pizza pizza") — 반복적이라 생성 품질 자체는 낮지만 주제는 확실히 학습됨. **실제 성능 확인(2026-09-11)**: personachat validation split 300개를 sbys/ltkm 재검증 때 바로잡은 방식(corpus-level SacreBLEU)으로 재니 BLEU-1 **17.03**(4-gram BLEU-4는 2.43) — 다만 BoB 논문 자체가 BLEU를 지표로 안 써서(PPL/Distinct/C-score/Fluency 등만 보고) 비교할 논문 수치가 없음. 그래도 실제 답변은 짧은 단일 예시 테스트 때보다 훨씬 자연스럽고 persona에 맞게 나옴(예: "i | `lmedr` | E | **실제 학습 완료 (2026-09-14), Family E 마지막 — ltkm/sbys/bob/orig/paa와 함께 전부 실제로 돌아감** — LMEDR(Chen et al., AAAI 2023, "Learning to Memorize Entailment and Discourse Relations for Persona-Consistent Dialogues") 래핑, https://github.com/Chenrj233/LMEDR. BART 인코더-디코더에 학습 가능한 "메모리" 코드북 두 개를 추가 — `memory1`(엔테일먼트 관계 프로토타입 10개, persona 문장만 인코더에 통과시켜 읽음)과 `memory2`(담화관계 프로토타입 10개, persona+history+query 전체를 인코더에 통과시켜 읽음)를 각각 softmax 가중합으로 읽어서 더한 뒤 디코더의 첫 `self.get_encoder()(...)` 대신 `self.forward(..., generate=True)`를 호출해서 `latent_variable`까지 같이 받아옴)를 공유 venv의 진짜 설치된 `transformers/`에 덮어쓰는 건 다른 모든 baseline을 깨뜨리는 명백히 위험한 작업이라 거부하고, 이 사설 벤더 복사본에만 적용. `xlibs_lmedr/file_utils.py`(+`onnx/config.py`/`onnx/convert.py` 3곳)가 `from transformers.utils.versions import ...`처럼 **자기 자신을 절대경로로 import** — 원본 그대로면 무해하지만 이름을 바꾸고 나니 이 venv의 진짜(호환 안 되는) ## 보류 중 — Family C

- **letta** (letta-ai/letta) — 조사만 하고 착수 안 함: 라이브러리가 아니라 FastAPI/SQLAlchemy 기반의 진짜 서버 애플리케이션이라, mem0/langmem/a_mem/memoryos/zep/hipporag처럼 클래스 하나 감싸는 걸로 안 되고 OpenAI 호환 로컬 프록시 서버 + subprocess 라이프사이클 관리가 필요함 — 다른 여섯보다 훨씬 큰 작업.
- **mem0의 그래프 메모리("Mem0^g")** — 조사만 하고 착수 안 함: 그래프 메모리가 Mem0 회사의 유료 호스팅 플랫폼 전용으로 옮겨가면서 현재 pip `mem0ai` 패키지엔 전혀 안 남아있음. `mem0ai==1.0.11` 같은 예전 버전엔 임베디드 Kuzu 그래프 옵션이 남아있지만, 이미 `mem0` baseline이 최신 버전을 pip 설치해서 쓰고 있어 같은 venv에 두 버전을 동시에 못 넣음 — vendoring해야 하는데 비용 대비 가치가 낮다고 판단해서 스킵.
- **MIRIX** (Mirix-AI/MIRIX, Apache-2.0) — 조사만 하고 착수 안 함, letta와 같은 체급: 단순 검색 라이브러리가 아니라 진짜 멀티 에이전트 개인비서 시스템(core/episodic/semantic/procedural/resource/knowledge_vault 6개 전문 메모리 에이전트 + meta-agent 오케스트레이터 + background/reflexion/auto-dream 에이전트 + 스크린 캡처 + 대시보드 + PostgreSQL 기반 하이브리드 검색) — 전체 7만 줄(agent 오케스트레이션만 5300줄, 이번 세션에서 가장 컸던 hypermem의 ~5000줄보다도 큼). README의 기본 사용법도 Docker Compose 백엔드 + 웹 대시보드 + 별도 `mirix-client` HTTP 클라이언트라 인프로세스로 그냥 생성해서 쓰는 구조가 아님. Docker 없이 쓰는 `mirix.sdk.Mirix`/`LocalClient` 경로가 있긴 하지만, LLM 연결부(`LLMClient.create()`)가 graphrag/lightrag처럼 함수·클래스 주입이 아니라 고정된 provider 문자열(openai/anthropic/google_ai 등) 팩토리라서 우리 공유 `llm.complete()`를 타게 하려면 그 팩토리 자체를 monkeypatch하거나 로컬 OpenAI 호환 프록시 서버를 따로 띄워야 함 — 사용자와 이번 세션에 확인해서 스킵하기로 결정.
- **MemOS** (MemTensor/MemOS, Apache-2.0) — 조사만 하고 착수 안 함, MIRIX와 같은 체급이거나 더 큼: 전체 91,000줄(MIRIX의 7만 줄보다 큼), mem_scheduler/mem_agent/mem_chat/multi_mem_cube/dream/plugins/api 등 수십 개 서브시스템을 가진 "메모리 운영체제" 플랫폼. README 자체 quick-start도 MemTensor 클라우드나 로컬 서버(`localhost:8000/product`)에 대한 HTTP 클라이언트라 MIRIX와 같은 패턴. LLM 연결부도 똑같이 고정 factory(`LLMFactory.backend_to_class`, openai/azure/ollama/huggingface/vllm/qwen/deepseek/minimax dict — config 쪽 `LLMConfigFactory`에도 똑같은 dict가 하나 더 있어서 두 군데를 다 monkeypatch해야 함, hipporag급 기법이지만 가능은 함). **결정적 이유**: LoCoMo 88.83점을 내는 실제 핵심 메모리 타입인 `TreeTextMemory`(그래프 구조)는 — 이번 세션의 다른 모든 그래프 baseline(zep의 임베디드 Kuzu, hipporag의 NetworkX/igraph, graphrag/lightrag/hypergraphrag/pathrag의 NetworkX)과 달리 — `graph_dbs/`에 임베디드 구현체가 아예 없고 `neo4j.py`/`neo4j_community.py`/`polardb.py`/`postgres.py`뿐임. 즉 파이썬 객체나 로컬 파일이 아니라 진짜 `bolt://` 프로토콜로 접속하는 Neo4j(또는 PolarDB/Postgres) 서버 프로세스가 실행 중이어야 함 — 이 저장소에서 처음 나오는 "진짜 외부 DB 서버" 의존성. 그래프 없이 벡터만 쓰는 더 단순한 타입(`NaiveTextMemory`/`GeneralTextMemory`)도 있지만, 그건 이미 만든 `mem0`(LLM이 사실 추출 → 벡터 스토어)랑 개념적으로 겹쳐서 MemOS를 추가하는 실질적 이유(트리형 그래프 메모리)를 반영 못 함 — 사용자에게 그래프 개념 차이(다른 baseline들의 "임베디드 라이브러리" vs MemOS의 "클라이언트-서버 DB")를 설명하고 이번 세션에 확인해서 스킵하기로 결정.

## 반복되는 패턴

위 중 여러 개가 스캐폴딩은 됐지만 end-to-end로 못 돌리는 이유는 데이터셋 쪽
(`plugins/datasets/**`, A의 lane)이 아직 안 따라와서입니다: adapter가 없거나,
해당 `task_type`용 `eval_items()`가 없는 adapter뿐이거나. 이게 막힌 이유일 때는
`db validate` + 실제(또는 실제와 같은 모양의) 데이터에 `complete()`/`embed()`를
mock해서 스모크테스트로 검증하고, 조용히 미검증 상태로 남기는 대신 그렇게
문서화해둡니다.
